## 1. 背景与目标

### 1.1 背景

当前 AgentForge 的 RAG 知识库仅支持上传 `pdf / docx / txt / md` 四类文档，用户如需将数据库类文件（如 SQLite 数据库、SQL 导出脚本、CSV 表格数据）纳入知识库，必须**手动**将其拆分成多个文本/表格片段后再逐个上传，体验差且容易遗漏或破坏数据完整性。

### 1.2 目标

> **用户上传数据库文件后，无需任何手动切片预处理，系统自动完成切片（分块）、向量化并入库。**

具体目标：

1. 第一期支持上传数据库/表格文件：`sqlite`（.db / .sqlite / .sqlite3）与 `csv`；SQL 导出脚本（.sql）与 Excel（.xlsx / .xls）列为后续阶段。
2. 上传后系统自动完成：解析 → 结构化切片 → Embedding → 写入 Qdrant，全过程无需人工干预。
3. 切片结果保留结构化元数据（表名、列名、行号等），提升检索准确率，并在问答来源引用中展示出处。
4. 沿用现有文档状态机（`PENDING → PROCESSING → READY/FAILED`）与重试机制，保证大文件/异常场景可恢复。
5. 上传时提供「切片方式」选项：用户可选择**自动切片**（系统默认策略）或**手动切片**（自定义切片参数/边界），两种方式均无需在本地预先拆分文件。

## 2. 可行性结论

**可以实现，且改造成本低。**

现有链路已包含自动切片的全部骨架：

```text
前端上传 /file/upload
  → 后端校验并落盘 /data/uploads/{agentId}/{uuid}.ext
  → document 记录（PENDING）
  → AI 服务 POST /rag/ingest
      → parse_file() 按扩展名解析为纯文本
      → chunk_text() 按 token 数切片
      → embed() 向量化
      → upsert 到 Qdrant collection（agent_{agentId}）
  → document 状态置为 READY / FAILED
```

本次功能只需做三件事：

| 改动位置 | 内容 | 工作量 |
|---|---|---|
| 后端文件模块 | 扩展允许上传的类型与校验 | 小 |
| AI 服务 RAG | 新增数据库解析器 + 结构化切片器 | 中 |
| 前端文件管理页 | 放开文件类型、切片方式选择（自动/手动）与预览 | 中 |

## 3. 名词约定

- **数据库文件**：本文档指承载结构化数据、可被程序化读取的表格/数据库类文件。**第一期仅覆盖 SQLite 数据库与 CSV**；SQL 导出脚本、Excel 列为后续阶段。
- **切片 / 分块（Chunking）**：将一份文件按语义或结构边界切分为若干可独立检索的文本片段，即 RAG 的 chunk。
- **结构化切片**：按“表 / 行 / 记录”为边界切片，而非按字符长度硬切，确保单条记录完整。

## 5. 需求详述

### 5.1 支持的数据库文件类型

**第一期（本期实现）：**

| 扩展名 | 说明 | 解析方式 |
|---|---|---|
| `.db` / `.sqlite` / `.sqlite3` | SQLite 数据库 | 只读打开，逐表逐行读取 |
| `.csv` | 逗号分隔表格 | 表头 + 按行/按批切片 |

**后续阶段（本期不实现）：**

| 扩展名 | 说明 | 解析方式 |
|---|---|---|
| `.sql` | SQL 导出脚本（INSERT 语句） | 按 INSERT INTO 语句拆分 |
| `.xlsx` / `.xls` | Excel 工作簿 | 逐 sheet 读取，按行/按批切片 |

> 说明：架构预留后续扩展能力，SQL / Excel / PostgreSQL dump / Parquet / JSON Lines 等可在后续阶段按同一模式接入，不改动现有管道。

### 5.2 核心交互流程（用户视角）

```text
1. 用户进入「文件管理」页，选择智能体
2. 点击「上传文档」，选择 .db / .sqlite / .sqlite3 / .csv 文件
3. 选择切片方式：自动切片（默认）或手动切片（展开参数配置）
4. 系统自动上传并触发入库，页面显示处理中（PROCESSING）
5. 完成后状态变为 READY，显示文件类型、切片方式、切片数（chunkCount）
6. 在对话中检索到该文件内容时，来源引用展示：文件名 + 表名 + 行号
7. 失败可点击「重试」，删除仍为全链路清理
```

### 5.3 非目标（本期不做）

- 上传后直接对数据库执行 SQL 查询（仅入库检索，不提供在线查库能力）。
- 数据库文件的增量同步（仅一次性全量导入）。
- 跨表关系建模与图结构检索。
- SQL 导出脚本（.sql）与 Excel（.xlsx / .xls）的解析入库（后续阶段）。

### 5.4 切片方式选项（自动 / 手动）

上传对话框新增「切片方式」单选，默认「自动切片」：

| 选项 | 说明 | 适用场景 |
|---|---|---|
| 自动切片（默认） | 系统按内置默认策略切片：文本类按 `chunk_size_tokens / chunk_overlap_tokens`，数据库类按结构化策略（每 chunk 行数等） | 大多数用户，零配置 |
| 手动切片 | 用户在展开的参数区自定义切片规则，可选「预览并调整边界」后确认入库 | 对检索粒度有特殊要求的用户 |

#### 手动切片可配置项（按文件类型）

| 文件类型 | 可配置项 |
|---|---|
| 数据库类（db/csv） | 每 chunk 行数、是否按表切分、是否排除指定列/表、是否保留表头 |
| 文本类（pdf/docx/txt/md） | chunk 大小（token）、chunk 重叠（token）、按标题/段落边界切分开关 |

#### 手动切片交互（建议）

1. 选择文件并切到「手动切片」→ 系统先做**快速解析预览**（读取结构，不入库）；
2. 用户修改参数 → 点击「预览切片」→ 前端展示前若干个 chunk 的内容与行号区间；
3. 确认后上传入库，`slicingMode` 与 `slicingConfig` 随上传请求提交，并持久化到 document 记录；
4. 入库失败重试时，沿用该文件保存的切片配置，无需重新填写。

> 说明：本期「手动切片」指**自定义切片参数 + 预览确认**；暂不做拖拽式逐块可视化编辑（可作为后续增强）。

## 6. 总体方案

### 6.1 架构分层

```text
┌─────────────────────────────────────────────────────────────┐
│ 前端 FileManage.vue                                          │
│   accept 放开 + 切片方式选择 + 预览 + chunkCount 展示 + 轮询    │
└──────────────────────────┬──────────────────────────────────┘
                           │ POST /file/upload
┌──────────────────────────▼──────────────────────────────────┐
│ 后端 FileServiceImpl.java                                   │
│   ① 扩展 ALLOWED_TYPES（+ db/sqlite/sqlite3/csv）             │
│   ② Magic Number 校验（防扩展名伪造）                          │
│   ③ 落盘 + 校验/持久化 slicingMode + slicingConfig            │
│   ④ document(PENDING) + 调用 AI ingest（透传切片配置）         │
└──────────────────────────┬──────────────────────────────────┘
                           │ POST /rag/ingest（X-Internal-Token）
┌──────────────────────────▼──────────────────────────────────┐
│ AI 服务 rag_service.py                                      │
│   ① parse_file() 新增 db/csv 解析分支                         │
│   ② chunk_database()/chunk_text() 按 slicingConfig 切片       │
│   ③ payload 增加 table / row 等元数据                        │
│   ④ embed() → Qdrant upsert（不变）                          │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 设计原则

1. **复用现有管道**：上传、落盘、状态机、重试、删除全部复用，只扩展“解析 + 切片”两个环节。
2. **结构化优先**：数据库文件按“表/行”切片，杜绝将一条记录拦腰截断；文本类文件维持现有按 token 切片。
3. **只读解析**：对 SQLite 以只读模式打开，不执行任何 SQL，从源头规避注入风险。
4. **可控性与可观测性**：保留每个 chunk 的出处（表名、行号），便于排查与引用。
5. **切片不依赖 LLM**：自动与手动切片的边界判断均由确定性代码完成，不调用对话模型（详见 7.7 节）。

## 7. 切片策略详述

### 7.1 通用约定

- 单个 chunk 的文本长度仍受 `chunk_size_tokens` 约束（约 750 字符，可按行拼接，超长则按行边界截断到下一 chunk）。
- 每条 chunk 追加元数据：`table`（表名/sheet 名）、`rowStart` / `rowEnd`（行号区间）、`file`。
- 空行、全空表跳过；单表总行数过大的按批次切，避免单次 Embedding 请求超长。
- 手动切片模式下，以上参数由用户提交的 `slicingConfig` 覆盖默认值。

### 7.2 SQLite（.db / .sqlite / .sqlite3）【第一期实现】

```text
只读打开 → 枚举所有表 → 逐表：
  读取列名（column_name）
  逐行读取 → 格式化为： "表 <表名>，第 N 行。列A: 值1；列B: 值2；..."
  每 K 行合并为一个 chunk（K 由 chunk_size_tokens 折算），保证整行不拆开
```

实现要点：

- 使用 Python `sqlite3`，连接时 `mode=ro` 只读打开（`file:path?mode=ro&immutable=1`），`PRAGMA query_only = ON`。
- 大表使用游标分批 fetch（如每批 1000 行），防止整表载入内存。
- 表名/列名转义后进入 payload，避免特殊字符破坏 JSON。

### 7.3 SQL 导出脚本（.sql）【后续阶段，本期不实现】

```text
读取纯文本 → 定位 INSERT INTO 语句 → 按语句（或按语句组）拆分为 chunk
DDL（CREATE TABLE）单独作为一个说明性 chunk： "表 <表名> 结构：<DDL>"
```

实现要点：

- 以 `INSERT INTO` 关键字为边界做轻量拆分，不做完整 SQL 解析（避免依赖重）；
- 单条 INSERT 极大（批量插入）时，按“行值元组”进一步切分，保证单条记录完整。

### 7.4 CSV【第一期实现】

```text
首行为表头 → 每行格式化为 "列A: 值1；列B: 值2；..." → 每 N 行合并为一个 chunk
```

实现要点：

- 使用标准 `csv` 模块，处理带引号/逗号/换行的字段；
- 编码探测：优先 UTF-8，失败尝试 GB18030（兼容中文 Excel 导出的 GBK/GB2312）；
- 无表头时以“第 N 行”作为行标识。

### 7.5 Excel（.xlsx / .xls）【后续阶段，本期不实现】

```text
逐 sheet：首行为表头 → 逐行格式化 → 每 N 行合并为一个 chunk
sheet 名写入 payload.table
```

实现要点：

- `.xlsx` 使用 `openpyxl`（只读模式 `read_only=True`），`.xls` 使用 `xlrd`（需确认依赖是否加入 requirements.txt）；
- 单元格统一转为字符串，日期按 ISO 格式序列化，避免 float 科学计数法噪音；
- 合并单元格等复杂样式不处理，仅取左上角值。

### 7.6 兜底策略

若数据库文件解析失败（损坏、加密、格式异常），捕获后走现有文本兜底（文件内容二进制不可读则报 `FAILED` 并给出明确错误信息），保证状态机不悬挂。

### 7.7 切片是否使用 AI 模型？

**切片环节不调用 LLM（对话模型），也不消耗模型 token。** 本文档中所有切片逻辑均为**确定性规则代码**：

- 自动切片：按 token/字符数（`chunk_size_tokens`）、按表/行边界（数据库文件）切分；
- 手动切片：按用户提交的行数、chunk 大小等参数切分，同样不经过 LLM。

与模型相关的只有两步，且均为系统既有配置：

| 环节 | 是否使用模型 | 使用哪个模型 |
|---|---|---|
| 解析 + 切片（chunking） | 否，纯代码规则 | 不使用任何模型 |
| 向量化（embedding） | 是 | 系统配置的 Embedding 模型（`EMBEDDING_MODEL`，默认 text-embedding-v3；未配置时走本地哈希 Mock） |
| 检索（retrieval） | 否，Qdrant 向量相似度 | 不使用模型 |
| 问答生成 | 是 | 系统配置的对话模型（`LLM_MODEL`，默认 qwen3.7-plus） |

> 补充：若未来引入**语义切片**（由 LLM 识别语义边界并生成 chunk 标题/摘要），届时才会调用系统配置的对话模型，但会显著增加成本与延迟，本期不做。

## 8. 数据模型与元数据变更

### 8.1 Qdrant payload 扩展

现有：

```json
{ "agentId": 1, "file": "demo.db", "chunkIndex": 0, "content": "..." }
```

新增可选字段：

```json
{
  "agentId": 1,
  "file": "demo.db",
  "chunkIndex": 0,
  "content": "...",
  "table": "users",
  "rowStart": 1,
  "rowEnd": 50,
  "sourceType": "sqlite"
}
```

- `sourceType`：`pdf / docx / txt / md / sqlite / csv`（第一期）；后续阶段追加 `sql / xlsx / xls`。
- `table / rowStart / rowEnd`：结构化来源定位，问答引用时展示“demo.db · users 表 · 第 1–50 行”。

### 8.2 document 表（可选增强）

`Document` 实体可增加以下字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_count` | int | 切片数（当前仅记录在 AI 返回中），便于列表页直接展示 |
| `slicing_mode` | varchar(16) | `auto` / `manual`，上传时选择的切片方式 |
| `slicing_config` | json | 手动切片的参数快照（每 chunk 行数、chunk 大小等），重试/覆盖时沿用 |
| `processed_chunks` | int | 已入库 chunk 数，入库期间由 AI 服务分批回写 |
| `total_chunks` | int | 总 chunk 数（解析切片完成后回写），列表页据此展示进度百分比 |

## 9. 接口变更

### 9.1 后端（复用现有接口，仅内部变化）

`GET /file/list`、`DELETE /file/{id}`、`POST /file/{id}/retry` 签名不变；`POST /file/upload` 增加可选切片参数（向后兼容）。

变更点：

```yaml
    max-size: 52428800    # 50MB，可配置
```

## 11. 性能与安全

### 11.1 性能

- **大文件异步化（强烈建议）**：当前 `ingest` 为同步调用，20MB+ 数据库解析+Embedding 可能超过后端 HTTP 超时。建议将 AI 服务侧入库改为异步任务（FastAPI `BackgroundTasks` 或简单线程池），后端 `upload` 立即返回 `PENDING`，由前端轮询/重试收敛状态。现有状态机已为此做好准备。
- 数据库解析采用分批游标，控制内存；Embedding 按 chunk 顺序调用，可引入并发（如 `ThreadPoolExecutor` 4 并发）加速，需注意远端 Embedding 限流。
- 文件上限（第一期默认，均可配置）：单文件 ≤ 50MB、总行数 ≤ 10 万行、表数 ≤ 100 张；超出直接拒绝并返回明确错误。
- 入库进度：AI 服务每处理一批 chunk 回写 `processedChunks / totalChunks`（直写 document 表），前端轮询展示百分比（见 8.2 / 9.3 节）。

### 11.2 安全

- SQLite 只读打开 + `query_only`，**绝不执行上传文件中的 SQL**。
- `.sql` 文件仅作文本拆分，不执行、不解析为可执行语句（后续阶段引入时沿用该约束）。
- 扩展名白名单 + 内容嗅探双重校验，防上传伪装文件。
- 解析异常统一走状态机 FAILED，不暴露堆栈详情给前端。

## 12. 测试与验收标准

### 12.1 单元测试（AI 服务）

| 用例 | 预期 |
|---|---|
| SQLite 两表各 10 行入库 | chunk 数正确，payload 含 table/rowStart/rowEnd |
| 单行超长（大字段） | 该行独立成 chunk，不与其他行混切 |
| CSV GBK 编码 | 中文不乱码 |
| 损坏/空数据库文件 | 状态 FAILED 或空内容报错，不悬挂 |
| 手动切片：自定义每 chunk 行数 | 按用户参数切分，slicingConfig 生效 |
| 手动切片：非法参数（如行数超限） | 后端/AI 返回明确校验错误，不入库 |
| 后续阶段：SQL 脚本 / Excel 解析 | 解析策略见 7.3 / 7.5 节，届时补充对应用例 |

### 12.2 集成测试

1. 上传 `.db` → 状态 `PENDING → PROCESSING → READY`，返回 chunkCount。
2. 对话检索命中后，来源引用展示文件+表名+行号。
3. 同名文件重新上传 → 旧向量被覆盖，无残留。
4. 删除文件 → Qdrant 向量、元数据、磁盘文件全部清理。
5. 上传超限/伪造扩展名 → 明确错误信息。
6. 手动切片上传：选择参数并预览后入库，列表展示切片方式，重试沿用原配置。
7. 大文件入库期间列表页显示处理进度（已处理/总 chunk），完成后显示总切片数。
8. 单文件超过 50MB / 10 万行 / 100 表 → 明确拒绝并提示具体超限项。

### 12.3 验收标准

- 用户上传数据库文件后，**全程无需手动切片**即可完成入库与检索。
- 所有新增文件类型与既有四种文档类型共存，无回归（`agentforge-ai` 现有 242 项测试保持全绿）。

## 13. 风险与注意事项

| 风险 | 影响 | 应对 |
|---|---|---|
| 同步 ingest 超时 | 大文件入库失败 | 入库异步化（第 11.1 节） |
| Embedding 远端限流 | 大批量 chunk 入库慢/失败 | 并发数可配 + 失败重试 |
| 编码不一致 | CSV 中文乱码 | UTF-8 优先，GB18030 兜底 |
| 扩展名伪造 | 解析异常/安全问题 | Magic Number 校验 |
| `.xls` 依赖旧库（后续阶段） | 兼容性问题 | 优先支持 `.xlsx`，`.xls` 评估后纳入 |
